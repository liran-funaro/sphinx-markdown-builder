# Review rules

These are the conventions the maintainer enforces most often in pull request reviews. Each rule says what the convention is, why it matters, and shows a change to flag ("Not this") beside the form to ask for ("This").

## Testing

### 1. Golden files (black-box tests)

**What:** Every behavior is tested from three parts:

1. **Input:** real reStructuredText in `tests/source/` or Python in `tests/my_module/`.
2. **Expected output:** the generated Markdown, committed in `tests/expected/`.
3. **The test:** `make test-diff` (part of `make test`) builds the sources and diffs the output against `tests/expected/`. `test_builder_make_all` in `tests/test_builder.py` builds the same sources under pytest.

The test already exists, so a new behavior only needs input and expected output. Ask for a test written by hand that builds docutils nodes or runs a separate `tmp_path` build to be moved into a fixture.

**Why:** Golden files test what users actually see, they keep working when the internals change, and the project keeps one test pipeline.

Not this:
```python
# tests/test_unit.py
def test_same_page_references(tmp_path):
    node = nodes.reference(refid="foo")
    mt.dispatch_visit(node)
    assert "](#foo)" in mt.astext()
```

This:
```rst
.. tests/source/links.rst

.. _same-page-target:

Same-page target
----------------

See :ref:`same-page-target`.
```
```markdown
<!-- tests/expected/links.md (excerpt) -->
See [Same-page target](#same-page-target).
```
```console
$ make test   # test-diff builds tests/source and diffs it against tests/expected
```
The expected file should be generated by the build, checked by eye, and then copied into `tests/expected/`.

### 2. Real fixtures

**What:** If a feature depends on a Sphinx extension or domain (Breathe, sphinx-design, the Python domain), the test should run that extension on real input. Faking the node structure it would produce isn't enough.

**Why:** A test only proves something if its node tree is one the extension really produces.

Not this:
```rst
.. tests/source/blocks.rst
.. py:function:: f(a[, b[, c]])
```

This:
```python
# tests/my_module/module_class.py
def optional_params(a, b=None, c=None):
    """Takes optional parameters."""
```

### 3. Reuse fixtures and build steps

**What:** New cases go into the `.rst` files and `Makefile` build steps that already exist. A new file or build step is justified only when the feature needs its own setup.

**Why:** Fewer fixtures and build steps mean CI runs faster and there's less to look after.

Not this:
```make
@echo "Building markdown with compact tables..."
@$(SPHINX_BUILD) -M markdown ... -D markdown_compact_tables=1
```

This: add `-D markdown_compact_tables=1` to the existing "Building markdown with configuration overrides..." step.

## Translator architecture

### 4. Declare simple nodes in `PREDEFINED_ELEMENTS`

**What:** A node that renders as a standard wrapper, an admonition box, a skipped subtree (`SKIP`), or a transparent container (`None`, which keeps processing its children) gets one entry in `PREDEFINED_ELEMENTS` in `translator.py`. A `visit_`/`depart_` method is for nodes that need real logic.

**Why:** Simple node handling stays in one table that can be read at a glance.

Not this:
```python
def visit_figure(self, node):
    return None

def depart_figure(self, node):
    pass
```

This:
```python
PREDEFINED_ELEMENTS = dict(
    ...
    figure=None,
)
```

### 5. Scoped state

**What:** State that only matters inside one kind of node lives in a `SubContext` subclass or a `ContextStatus` field. It shouldn't be an attribute on `MarkdownTranslator`. Each status flag means exactly one thing.

**Why:** A translator attribute is visible to every node and is easy to leave in the wrong state. A flag reused for a second meaning breaks the cases it wasn't designed for. For example, comments turn off escaping but still collapse line breaks.

Not this:
```python
self._first_param = True  # in MarkdownTranslator.__init__

if flavor == "github" and self.status.escape_text:  # escape_text standing in for "keep newlines"
```

This:
```python
self._push_context(CommaSeparatedContext(", "))  # state lives with desc_parameterlist

self._push_status(escape_text=False, preserve_line_breaks=True)  # one flag, one meaning
```

### 6. Single pass

**What:** Collect information while the visitor walks the tree, and build the final output in `astext()`. A separate pass over the tree in `visit_document` adds work the translator doesn't need.

**Why:** A single pass is simpler and matches how the translator already works.

Not this:
```python
def visit_document(self, node):
    for abbr in node.findall(nodes.abbreviation):
        self._abbreviations[...] = ...
```

This:
```python
def visit_abbreviation(self, node):
    self._abbreviations.setdefault(node.astext(), set()).add(node.get("explanation", ""))
    # footnotes rendered in astext()
```

### 7. Tree comments

**What:** When code depends on a node shape that isn't obvious (which attribute is set, which parent appears), a comment should describe that shape. The existing comments on `desc` and `table` show the style. `make doc-xml` prints the real doctree.

**Why:** The doctree differs between directives and domains, and the next reader can't see it from the Python alone.

Not this:
```python
if node.get("refuri"):
    target = ...
elif "filename" in node:
    target = ...
else:
    target = node.get("reftarget", "")
```

This:
```python
# download_reference: `refuri` is set for external URLs, `filename` for
# files Sphinx copied into _downloads, and `reftarget` for unresolved refs.
```

## Code style

### 8. Inline single-use code

**What:** A helper method with one caller is written at that call site. Indirection that only forwards a call gets folded into its target.

**Why:** The maintainer discourages tiny single-use methods "as a general rule". They make the reader jump around the file to follow the logic.

Not this:
```python
def _visit_doc_info(self, node):
    self._add_doc_info_value(name, value)

def _add_doc_info_value(self, name, value):
    self._doc_info[name] = value
```

This:
```python
def _visit_doc_info(self, node):
    self._doc_info[name] = value
```

### 9. Idiomatic Python

**What:** Use the obvious built-in for each job: `set` for sets, unpacking in `for` loops, a plain `if`/`else`.

**Why:** A clever workaround makes the reviewer stop and work out why it was needed.

Not this:
```python
anchors = dict.fromkeys(node.get("ids", []) if "refuri" not in node else [])
for source in self.env.dlfiles:
    dst = self.env.dlfiles[source][1]
```

This:
```python
for anchor in set(node.get("ids", ())):
    self._add_anchor(anchor)
for src, (_, dst) in self.env.dlfiles.items():
    ...
```

### 10. Clear names

**What:** A name says what it holds and why. When two related attributes could be confused, a one-line comment explains how they differ.

**Why:** With a vague name, the reviewer has to trace the code to find out what it's for.

Not this:
```python
self._doc_info_configured: Set[str] = set()
```

This:
```python
# Fields set from conf.py; these take priority over fields set in the document.
self._doc_info_from_config: Set[str] = set()
```

## Scope and design

### 11. Focused PRs

**What:** A PR covers one fix or one feature. Anything else the author improves along the way goes in its own PR.

**Why:** The maintainer has limited time. Focused PRs get merged; mixed ones wait or get asked to be split.

Not this: one PR that adds abbreviation footnotes and also renders figure captions.

This: PR A adds abbreviation footnotes. PR B renders figure captions.

### 12. General solutions

**What:** Fix the general problem rather than one case. Make behavior configurable when users could reasonably want different options. A fix should work for every language domain.

**Why:** The builder serves every Sphinx domain and every kind of raw content, and a narrow fix can quietly break the cases it didn't consider.

Not this:
```python
markdown_exclude_html = True   # actually drops *all* raw nodes
```

This:
```python
markdown_include_raw_types = ["markdown", "html"]
```

## Project hygiene

### 13. Lint limits in `pyproject.toml`

**What:** When pylint complains because of a project-wide limit, the limit is adjusted under `[tool.pylint.format]` in `pyproject.toml`. An inline `# pylint: disable` is for one specific exception on one class or line.

**Why:** Each limit lives in one place, which stops the same disable comment spreading across the code.

Not this:
```python
def __init__(  # pylint: disable=too-many-positional-arguments
```

This:
```toml
[tool.pylint.format]
max-positional-arguments = 6
```

### 14. Release-neutral changes

**What:** A PR leaves version strings alone, because the maintainer bumps them with `bumpver` at release time (see `AGENTS.md`). New syntax has to run on every Python version that `requires-python` in `pyproject.toml` allows.

**Why:** Version bumps in PRs cause conflicts between PRs, and syntax newer than `requires-python` allows breaks CI.

Not this:
```diff
-__version__ = "0.6.11"
+__version__ = "0.6.12"
```

This: the diff leaves `__version__` and `[tool.bumpver] current_version` unchanged.
